# WebDCC 实施约束与改动预算

> 版本1.0；日期2026-11-14（Asia/Shanghai）；基线 `9b1ae9096c19162206361e3910b7ef2592c5f30b`。  
> 对应 `WebDCC_NATIVE_PARITY_SPEC.md` 的48个NP需求。此文件是实施约束和工程估算，不是现有实现或测试完成声明。

## 1. 重构结论

**需要重构，但不应整仓重写。** 已有monorepo分层、原生adapter、SQLite追加事件、文件存储、React界面、离线缓存和回放机制值得保留。严重问题集中在协议合同、原生状态归约、持久命令、连接代际与证据门禁；仅拆大文件或更换框架不会自动解决这些问题。

基线实测共有1,701个跟踪文件。统计手写生产TS/TSX/JS/CSS为87文件、17,863物理行；其中CSS 2,205行的index.css属于样式规模，不按其长短判架构失败。另有761份生成Codex类型、8,495行，不是761个手写业务模块。测试63文件/5,779行，测试基础设施12文件/2,148行，脚本33文件/4,945行。这些统计不含JSON schema和大fixture。以此作为预算锚点，不能用整个仓库文件数估算重写成本。

保留技术栈：TypeScript、Fastify、React/Vite、SQLite、pnpm workspace。默认不引入微服务、Redis、Kafka或新数据库，不fork原生Agent模型循环。

## 2. 不可妥协的实现约束

| 编号 | 约束 | 必须提供的检查 |
|---|---|---|
| C01 | 原生版本与能力有明确基线；禁止拿新官网接口直接假定旧binary支持 | version/schema/manifest fingerprint，未知版本受限 |
| C02 | 不自动注入系统提示、开发者指令、工具、MCP、skills/hooks或子Agent定义 | launch spec与direct native配置对比；显式诊断/用户配置动作单列 |
| C03 | 用户文本逐字透传；原生控制使用typed action，不隐藏改写prompt | 文本字节、content part身份、原生请求对照 |
| C04 | 不静默写用户配置；显示目标Host、作用域、diff和持久性 | revision/CAS、原子写、错误后原文件不损坏；远程Host不写本机home |
| C05 | 权限遵守原生默认与实际状态；不把requested当effective | inherit与切换/换模型/恢复的真实执行验证 |
| C06 | 已知native方法必须类型化与运行期验证；未知反向请求不得猜批准 | schema合同测试；string/number ID原样保留 |
| C07 | 每个命令先持久接收后ACK；队列不是内存数组 | 并发同ID、冲突payload、各崩溃窗口与uncertain恢复 |
| C08 | 不承诺不可证明的exactly-once外部副作用 | native identity对账；不确定时阻止盲重放并显式提示 |
| C09 | 原生事件先保真再投影；明确raw敏感信息策略 | native envelope、source identity、projectionVersion、unknown去向 |
| C10 | 生产与回放同一语义路径；参考答案独立 | 同输入一致性+原生对照，禁止replay专用补造事件 |
| C11 | 同一interaction一份权威状态；答案/审批native成功前不能显示完成 | 多浏览器、过期、取消、拒绝、重试和secret用例 |
| C12 | Web服务、native运行时、浏览器各自重连分别验收 | 独立断开、kill/restart、过期认证、迟到回调矩阵 |
| C13 | 结构化与native surface共享identity；平台fencing只约束本服务托管连接 | 对external owner另验native锁/释放/仲裁；无证据则blocked，失败不得伪装无缝接管 |
| C14 | 主应用origin不运行不可信HTML/SVG/MCP UI | 主动内容下载/隔离origin/CSP；认证Origin检查 |
| C15 | 完整诊断录制、Watchdog和类似平台扩展显式开启、标来源 | 默认配置、启动参数、保留期限、secret写盘前脱敏 |
| C16 | 每条功能有用户可操作闭环；JSON存档不算完成 | 触发→动作→native结果→Web结果→恢复证据 |
| C17 | 每个报告绑定当前构建和环境；未触发/未运行不能当通过 | SHA/Agent/Provider/OS/场景谓词，失败也生成新报告 |
| C18 | 所有新增状态的迁移保留旧sessionId/URL和历史 | 真实旧库迁移、附件hash、降级/恢复演练 |
| C19 | Native UI/CLI不是无限制RPC/shell代理 | 固定目标/argv/cwd、认证、最小消息桥、无任意URL透传 |
| C20 | 图表、快照、schema、lockfile不用于凑业务LOC或覆盖率 | 手写实现/测试/生成/移动/数据量分别统计 |

上述约束应用于实现行为；它们不创造额外用户审批流程。本次交付仅是评审与文档，没有运行发布、写原生配置、登录账号或调用真实模型。未来代码中安装插件、修改权限、共享或发布等用户动作，按该动作实际影响提供可审阅的界面。

## 3. 行数与文件数的统一口径

**实现行数**：该需求中人工维护源码的新增行+实质修改行，包含前后端及必要协议/配置代码。不把一行替换按“删一行+加一行”计两次。**测试行数**单列。它们是实施工作量，既不是净增，也不是最终仓库diff去重后的行数。

不计入实现预算：生成TS/JSON schema、lockfile、采集轨迹/截图、vendored第三方库、纯格式化、纯移动代码以及本文档。删除和纯移动单独报告。跨需求可能重改同一模块；公共基础层只在自己的NP计主要建设成本，后续功能只计接线/扩展。原始三份专项报告互相重叠，不能再叠加到本表。

**文件数**：完成该需求预计触及的源码、测试和必要配置文件的去重数量，包含新增和已有文件。它不是新增文件数；也不能把48行相加得出最终仓库独立文件数。新增/修改拆分要在设计spike后产出具体file plan。当前只对每项提供可解释区间，避免假精确到“必改17文件”。

置信度：高约±25–35%，中约±40–60%，中低/低需先做合同或原生surface验证。范围是规划估计，不是硬性写够/写少的要求。UI/SDK已有可用原语的修复更可估；动态插件、身份迁移和上游未公开能力不可用行数保证。

## 7. PR规模与变更纪律

- 默认每PR一个可验证行为或一个纯提取边界，业务实质修改目标400–800行，触及4–8个主要文件。测试可超出业务行数，数据/生成代码另计。
- 持久队列、交互协议和数据迁移跨层项可超过软上限，但PR描述须给出不可再拆理由、兼容策略与回滚点。软上限不是要求多次问用户批准。
- 纯移动与行为修复尽量分PR：前者要求输出一致；后者要求新缺陷复现先失败再通过。禁止一个PR同时换框架、改schema、重绘UI和新增native能力。
- 超出该需求预算上限30%时更新估算与分解，而不是删验收或降低原生语义。预算上涨是规划信息，不是自动阻止必要工作的审批机制。
- 每PR描述必须说明当前问题、改变后的行为、native合同、测试证据、数据迁移和剩余限制；不写空泛“优化体验”。
- 不改生成schema迎合错误实现；不重写黄金文件让测试变绿；不删除失败的场景；不以skip/notTriggered冒充pass。
- 不把本次review复现脚本里的stub/fake路径带入生产；凭据与实际服务器地址不得提交。

## 8. 故障测试矩阵

| 故障窗口 | 必须得到的结果 |
|---|---|
| 浏览器写入outbox前/后关闭 | 已承诺持久的草稿/命令可恢复，未承诺部分明确 |
| server收到请求、占有commandId前后 | 同payload重试不重复创建命令，异payload冲突 |
| queued但native尚未接收时kill | 队列正文、附件和位置保留，取消仍有效 |
| native接受但server未落确认时kill | native查询能对账或标uncertain，禁止自动盲重发 |
| 审批回复发送中断网 | 不提前resolved；恢复后查询/重试按原生幂等语义 |
| 原版页面已批准/回答/取消 | Web权威投影更新，旧卡不再提交 |
| WebSocket单层断开 | 区分browser↔WebDCC与WebDCC↔native，两层分别恢复 |
| Host重启/更换cookie/profile | generation变更，旧交互/owner失效，必要时重新登录 |
| 换模型后旧query迟到 | 旧generation不污染新消息/权限/task |
| 首屏分页请求失败 | 不推进已覆盖游标，后续重试补缺口 |
| 主动内容文件或恶意资源 | 不获得主origin权限，不能调用已认证命令 |
| native surface接管中断 | WebDCC托管域内没有双writer；外部owner有原生锁/释放/仲裁证据，否则blocked；可解释当前owner及恢复路径 |

## 9. 发布判定与诚实声明

可发布“可靠统一工作台”：M0通过，目标高频能力的M1证据满足门槛，剩余native能力清楚列缺口。此标签不等于“全原生”。

可发布“统一UI全功能”：除前项要求外，所有N中的能力在统一结构化UI完成，不能计native后备入口。动态插件增加能力时重新计算分母。
